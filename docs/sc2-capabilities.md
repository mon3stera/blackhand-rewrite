# SC2 银河引擎能力边界（重写项目的硬约束）

> 目的：任何在 TS/Python 里设计的规则核心，**必须能映射成 Galaxy 脚本 + 数据编辑器条目**。
> 本文件是设计输入，不是参考资料。凡是与本文件冲突的设计，一律以本文件为准。
>
> 实证来源：黑手升温 `MapScript.galaxy`（87,973 行、776 函数、424 触发器）的 API 使用统计，
> 以及 SC2 1.5.0 之后的语言扩展与社区工具链现状。

---

## 一、原图实证：引擎能力清单（它做到了什么）

| Camera | 4,257 | `CameraInfoFromId`(534)、`CameraApplyInfo`(359)、`CameraPan` |

## 二、语言层：Galaxy 的硬限制

| 特性 | 状态 | 对设计的影响 |
|---|---|---|
| 数组 | ✅ 支持，**固定长度**，可多维（原图大量 `int[16][2]`） | 所有"动态结构"（角色列表、事件队列、玩家集合）都要用固定数组 + 计数器模拟 |
| 字符串 | ⚠️ 基本操作（长度/截取/查找/大小写/转数字） | 无正则、无格式化库；文案一律走字符串表键（`StringExternal("Param/Value/xxx")`） |
| 结构体 struct | ⚠️ 1.5.0 后语言支持（islga《1.5.0 指针归来》），但**原图完全没用**，需实测编译器支持度 | 不要假设可用；数据一律用"平行数组 + 索引约定"表达，必要时再引入 |
| 函数指针 / 函数引用 | ⚠️ 同上（1.5.0 引用语法），原图用 if/switch 分发而非函数表 | 角色钩子分发先按"代码生成 switch"实现，函数引用作为可选优化 |
| OOP / 继承 / 泛型 / 模板 | ❌ 无 | 角色行为不能靠多态，只能靠数据表 + 分发函数 |
| 闭包 / lambda | ❌ 无（引用语法是否等价闭包需实测） | 回调必须落成具名全局函数 + 显式参数 |
| 动态内存 / GC | ❌ 无 | 无 new/delete；对象生命周期由引擎管理，自建容器必须预分配 |
| 异常 / try-catch | ❌ 无 | 所有错误路径必须显式判断；无"失败恢复"机制 |
| 反射 / 元编程 / 宏 | ❌ 无 | **表驱动只能靠外部代码生成器**（从规格生成 Galaxy 源码），不能运行时反射 |
| 文件 IO / 网络 | ❌ 无 | 唯一持久化通道是 Bank（存档），且签名/校验要自己实现；不能联网、不能读写本地文件 |
| 线程 | ⚠️ 触发器协程模型：每个触发器独立线程，`Wait` 挂起当前线程 | **这是原图 bug 的主要来源**：Wait 期间全局状态可能被其他触发器改变，必须设计"状态快照 + 阶段屏障" |

## 三、运行时层：能做什么 / 不能做什么

### ✅ 可以做

- **事件驱动**：聊天消息（`TriggerAddEventChatMessage`）、周期事件（`TriggerAddEventTimePeriodic`）、单位/区域事件、**对话框控件点击**（`EventDialogControl`）——原图的整套交互就靠这几类。
- **UI**：`Dialog` + 控件（按钮、标签、图片、列表、编辑框、进度条）可编程创建/更新，支持坐标、大小、颜色、可见性、启用态、提示；文本支持富文本标签（`<c val="RRGGBB">`、`<s val="样式">`、`<n/>`、`<img path="..."/>`，已实测）。
- **多玩家同步**：引擎保证同步，`RandomInt`/`RandomFixed` 是同步随机（多人一致）。
- **表现层**：单位创建、Actor 动画、镜头、音效、屏幕闪烁、淡入淡出。
- **数据编辑器**：单位/技能/效果/行为/按钮/图标/模型等 Catalog 条目（XML 文本，可程序化生成，但需要编辑器/游戏校验）。
- **存档**：Bank 读写（原图用它做积分/成就/模型解锁的持久化，含自研签名）。
- **调试**：Debug 触发器 + 聊天命令 + 系统消息（无断点式调试，需要自建日志与强制状态命令）。

### ❌ 做不到 / 代价极高

- 任何形式的外部通信（HTTP、文件、进程）——**AI 无法在游戏内接入外部服务**。
- 运行时加载/修改代码、插件化角色包——角色必须在编译期确定。
- 复杂 UI 布局（大量控件的像素级排布靠脚本计算，维护成本高；`.SC2Layout` UI 模块可缓解但需编辑器）。
- 高帧率/大量实体的表现（触发器线程与 UI 刷新有性能开销，原图明显做过节流）。
- 无锁并发的复杂逻辑（协程 + 全局状态，容易出现竞态，需要显式阶段化）。

## 四、对架构的硬性约束（设计必须遵守）

1. **规格 → 双目标生成**
   一份角色/规则规格（数据表 + 状态机定义）生成两个产物：
   - TS/Python **模拟器**（自动跑数千局，验证规则、找死角、调平衡）
   - **Galaxy 源码**（SC2 运行实现）
   规格是唯一事实源；两个产物不得各自演化。

2. **状态显式化 + 阶段屏障**
   所有跨阶段状态写成全局平行数组（`gv_role[16]`、`gv_alive[16]`…），
   每个阶段（Prep/Kills/After/CheckEnd）结束前做一次"状态一致性检查"，
   禁止在 `Wait` 期间依赖可变全局量的旧值。

3. **分发用生成代码，不用多态**
   角色钩子（夜间行动、结算、判胜、交互）用生成器产出 `switch` 分发函数；
   若实测确认 1.5.0 函数引用可用，再作为优化替换（接口不变）。

4. **文案与素材零成本复用**
   字符串走原 `GameStrings`/`TriggerStrings` 键表；贴图/模型/音效引用沿用原图与 `Mafia Assets A`/`mm2`/`mm3` 的路径。

5. **可测试性内建**
   调试命令（强制角色、跳到指定阶段、打印状态）从第一天就设计进去；
   模拟器与游戏内行为必须由同一份规格驱动，避免"两边不一致"。

| # | 待验证 | 方法 | 阻塞什么 |
|---|---|---|---|
| 1 | luna 能否编译目标版本脚本 | 编译一份最小 galaxy | 整个工具链 |

| 4 | 数组上限、全局变量上限、触发器线程上限 | 压测样例 | 数据模型规模 |
| 5 | Dialog 控件数量/刷新频率的实际上限 | 压测 UI | UI 架构 |

> 第 1、2 项是"整个重写是否可行"的前提，应最先做。

## 六、结论

- **能力上完全够**：原图 8.8 万行脚本用 293 个 API 实现了完整社交推理游戏，说明引擎能承载我们要做的一切。
- **语言上要克制**：无 OOP/闭包/动态结构/异常，一切靠"固定数组 + 显式状态 + 生成代码"。
- **架构上必须双目标**：模拟器用于测试（解决"10 人测试"瓶颈），Galaxy 用于运行，规格唯一。
- **风险集中在工具链**（第 1、2 项实测），而不是游戏设计本身。
